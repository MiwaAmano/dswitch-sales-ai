# 実在企業リサーチ連携案

状態：最新の進捗は [gBizINFO接続ガイド](gbizinfo-setup.md) を参照。画面はgBizINFOの接続確認・設定案内に切り替え済み。公式資料確認待ちのため実API通信は停止し、サンプル結果も表示しません。以下は当初の比較・設計案です。Google Placesの接続は保留中です。

## 現状

Next.js 15 App Router / TypeScript / Tailwind CSS。app/page.tsxはクライアントコンポーネントで、lib/sales.tsのsampleResearchProviderが架空企業12社を検索します。営業リスト・履歴・下書きはlocalStorageのdswitch-sales-v1に保存されます。サーバーAPI、認証、共有DBは未実装です。公式ロゴはpublicにあります。

Company型は従業員数を必須numberで扱い、メールにも人数を埋め込みます。この型へ実データの欠損を0として流し込むと、人数を事実と誤認するメールになります。実データを有効化する前にnullable対応と「未取得」の表示、欠損項目を省くメール、CSVの空欄対応が必要です。既存レコードはそのまま読み込める後方互換変更にし、保存キー・履歴・下書きを保持します。

## 推奨

第一段階はgBizINFOを第一候補として、現行APIで利用できる項目と再利用条件を確認することを推奨します。日本の法人に対する検索・法人番号による識別を営業管理の軸にします。条件を満たせない場合は、CRM保存用途を契約上認める企業データサービスの契約を比較してから切り替えます。

| 候補 | 向く用途 | 不足・注意 | 料金の扱い |
| --- | --- | --- | --- |
| gBizINFO（政府法人情報） | 日本法人の基本情報、法人番号による識別 | 法人名・所在地が中心。業種・従業員数・公式サイト等は収録範囲と現行APIの確認が必要。連絡先や網羅性は保証しない | 無償提供の政府APIとしての候補。ただし本環境から最新案内は参照できておらず、現行条件・上限を確認してから有効化 |
| Google Places API (New) | 地域・名称・施設カテゴリから実在拠点を発見、公式サイトの候補を確認 | 法人登記DBではない。支店・店舗が混在し、従業員数やデスクワーク比率は提供を期待しない。Placesの情報をそのまま永続CRM・CSVに蓄積する設計は採用しない | 決済登録・従量課金。Text Search、Details、要求フィールドでSKU・単価が変わる。websiteUri等の取得は上位SKUになり得る。無料枠超過や複数呼び出しで費用発生 |
| CRM用途を許諾する商用企業DB | 業種・規模・Webサイトによる絞り込みと営業リスト保存 | 契約ごとの対象地域・件数・保存／CSV／営業利用条件確認が必要 | 見積・契約が必要。契約前に呼び出さない |

Google Placesは、place ID等の例外を除く保存・キャッシュ制限、表示時のGoogle Mapsおよび第三者帰属表示、利用目的・再配布等の条件確認が必要です。公式サイトURLを含むGoogle由来の項目を、単にCRMへコピーしただけで自社独自情報とは扱いません。独立した出典から取得した情報も、その出典の利用条件を別途確認します。Googleの保存制限に一律「30日保存なら可」という想定は置きません。gBizINFOにも出典表示・第三者権利等の現行条件を確認します。

API応答に含まれたURLも、企業自身の正当な公式サイトかは未確認の場合があります。その場合は「公式サイト候補」と表示し、人が確認します。存在しない項目をLLMで補完しません。名称や所在地だけで「法人の同一性を確認済み」としません。

## 検索と評価の仕様案

- 全国／都道府県／市区町村、APIに収録された業種、キーワードで検索。全国は日本を対象にした検索条件であり、全国企業の全件取得を保証しない
- ページ単位の少件数取得から開始。外部サービスの上限とページングをそのまま案内し、全国一括の自動巡回は行わない
- 各項目を取得値と出典URL・提供元・取得日時の組で保持。欠損はnullとし「未取得」と表示する
- 業種が取得できる場合のみ、情報通信・専門サービスなど対象業種に基づく候補として優先表示する。業種がない企業を勝手に推定分類しない
- 「相性」はAIによる事実認定や成約確率ではなく、根拠付きの営業上の仮評価。最初は点数や成功確率を付けず「業種に基づく候補／要確認」とする
- d switchの対象規模、提供地域、具体的な提供内容、最低利用人数等は未確認。ユーザーの条件が明確になり次第、説明可能なルールを追加
- 登録前に出典別の保存条件を検証。取得日時、出典、法人番号を引き継ぎ、未接触で追加する。既存の企業・履歴・下書きは上書きしない
- 法人番号を優先して重複確認。place IDは拠点の識別であり、同一法人の別拠点まで識別できるわけではない。法人番号のない結果は人による重複確認を追加

## 連携構成

ブラウザーの検索画面 → Next.jsのサーバーAPI → サービス別アダプター → 外部サービス、という順番にします。APIキーや外部サービスのレスポンス全文をクライアントへ渡しません。サーバーで入力制限・固定した接続先・タイムアウト・要求フィールド・結果件数・正規化・エラー変換・利用量制限を管理します。生の外部エラーやキーはログや画面に出しません。ブラウザーから任意URLを取得させる機能は作りません。

認証のない公開サーバーに有料APIをつなぐと第三者による課金悪用が可能です。Windowsの自分専用の試験では127.0.0.1への待ち受けに限定し、外部には公開しません。共有利用する段階では、認証・権限・サーバーDBによる利用量カウンター等を先に実装します。クライアントのボタン無効化やメモリ内だけの回数制限は課金防止の保証になりません。

Googleを採用する場合は利用SKU・料金表・月間の想定検索回数を確認し、呼び出し前に予算を決めます。予算アラートだけでは請求は止まりません。設定可能なAPIクォータ、アプリ側の日次／月次の停止条件、ページング・詳細取得の上限を併用し、初回テスト自体が課金対象になり得ることを説明してから実行します。現段階では無料と断言したり、課金APIを実行したりしません。

## 開発済みの準備

lib/research.tsに以下を独立して追加しています。まだ画面・既存Company・localStorageへは接続していません。

- ResearchCandidate / Evidence：取得元・取得日時付きの欠損可能な実データ型
- RealResearchProvider：サーバーアダプター用のインターフェース
- assessFit：取得した業種のみを使う、根拠と限界付きの仮評価
- candidateIdentityKey：法人番号優先の識別
- checkPersistence：利用条件レビューがない出典は保存不可。Google由来項目のCRM保存はこの段階では不可
- 6つのテスト：未取得とゼロの区別、仮評価、識別、未確認の保存条件、混在出典、壊れた出典

checkPersistenceは法的条件の自動判定ではありません。レビュー情報は人による確認後にサーバー設定として渡す必要があり、画面のチェックボックスやユーザーの送信値を信頼してはいけません。

## 初心者向け：ユーザーが行うこと

最初はgBizINFO案を推奨します。最新仕様・利用条件が確認できるまで、キーの発行やGoogleの課金有効化を急ぐ必要はありません。

1. gBizINFO公式サイト（https://info.gbiz.go.jp/）のAPI利用案内を確認し、案内に従って利用申請します。画面名や申請方式は変更されることがあります
2. 利用目的は「自社の法人営業候補調査・営業管理への利用」とし、保存・CSV出力の条件も確認します。条件上問題がある場合は登録方法を変えます
3. 発行されたキー／トークンはチャットへ貼らず、GitHubにもアップロードしないでください
4. アダプター実装時の指定名はGBIZINFO_API_TOKENを予定。Windows側のプロジェクト直下の.env.localに保存します。ファイルは.gitignoreの.env*で除外済みです。設定後は開発サーバーを再起動します。NEXT_PUBLIC_で始まる名前は使いません
5. クラウドへ設定する場合は環境設定のシークレット欄を使用し、実際のAPI接続先に限定して設定します。現行APIのホスト確認前に接続先やURLを推測して登録しません

Googleを選ぶ場合は別途Google Cloudのプロジェクト作成・請求先設定・Places API (New)の有効化・専用キー発行が必要です。API制限はPlaces API (New)に限定し、サーバーから使うキーは可能な環境では送信元IPにも制限します。HTTPリファラー制限のブラウザー用キーをサーバー用キーの代わりにしません。WindowsのIPが変わる場合は固定IPのサーバー等の運用方式を先に検討します。キーはGOOGLE_PLACES_API_KEYとしてサーバー側だけに保存します。

## 次の実装順

1. 公式の最新API仕様・規約・料金を参照可能にし、採用サービスを確定
2. 認証やWindows限定の運用範囲、取得項目・保存範囲を確定してサーバーアダプターと検索APIを実装
3. リサーチ画面に実データモード、未取得表示、出典、仮評価、登録確認を実装。実データの検索失敗時はサンプルへ切り替えずエラーを表示
4. 従業員数等の欠損に対応する後方互換の変更、出典の保存、重複確認、メール生成・CSVの実データ対応
5. 認証・件数制限・エラー・移行・既存データ保持をテスト
6. キー設定と料金合意の後に少件数で実API検証。返された事実・出典・保存条件を確認し、準備完了とする
